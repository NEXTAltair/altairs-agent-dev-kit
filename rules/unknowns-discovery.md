# Unknowns Discovery Rules

AI エージェント作業で、プロンプト・ルール・計画に書かれていない前提を推測で埋めないための
汎用ルール。実際の作業対象（コード、仕様、ユーザー意図、運用環境、制約）と、エージェントに
渡された情報との差分を **unknowns** として明示し、調査・質問・仮定・延期のどれで扱ったかを残す。

## 核心ルール

**推測で進める前に unknown を分類する。** unknown はすべて質問すればよいわけではない。
ローカル調査やテストで確定できるものは自分で確認し、ユーザー意図やスコープ判断に関わるものだけを
質問する。軽微で可逆な判断は保守的に仮定してよいが、仮定として明示する。

## 適用条件

- 新機能、バグ修正、設計変更、複数ファイル変更、PR 作成を伴う作業
- 要件が曖昧、または成功条件・検証方法・不変制約が不足している作業
- 既存設計や過去判断との整合が必要な作業
- 実装中に当初の計画と矛盾する事実を見つけた作業

## スキップ可能な条件

- typo 修正、コメント修正、フォーマットのみの変更
- 1 コマンドで完了し、結果が直接観測できる read-only タスク
- 同一セッションで同じ unknowns を既に整理済みで、前提が変わっていない場合

## 入口: 作業前の unknowns 棚卸し

着手前に、作業のリスクに応じた粒度で以下を確認する。小さな作業では口頭の短い整理でよい。
設計変更や複数ファイル実装では、計画・PR description・作業メモのいずれかに残す。

```markdown
## Known Facts
- 確認済みの事実

## Unknowns
- 未確定だが作業結果に影響すること

## Assumptions
- 未確認のまま進める仮定と、その理由

## Resolution Plan
- inspect: ローカルコード / docs / ADR / logs で確認するもの
- test: テスト / smoke / reproduce で確認するもの
- ask: ユーザーに確認するもの
- defer: 今回のスコープ外として明示するもの
```

## unknown の分類

### inspect: 自分で確認する

以下は原則としてユーザーに聞く前に確認する。

- 既存コードの構造、呼び出し関係、命名規約
- ADR、設計メモ、過去の教訓、最新計画
- 依存関係、設定、CI、実行環境
- ログやテスト失敗から分かる実際の挙動

関連ルール: [planning-memory.md](planning-memory.md)、[testing.md](testing.md)。

### test: 実行で確認する

以下は推測ではなく、再現・テスト・静的検査で確認する。

- バグの再現条件
- 修正が目的の挙動を変えたこと
- 既存挙動を壊していないこと
- パフォーマンス、I/O、外部境界など、コード読解だけでは確定しない挙動

実 API や実モデルなど決定論的でない検証は、CI 必須ゲートと分けて扱う
([testing.md](testing.md) 参照)。

### ask: ユーザーに確認する

以下について、既存のユーザー指示・承認・リポジトリの契約から判断できず、結果を左右する場合は確認する。

- 成功条件、受け入れ基準、優先順位
- スコープに含める / 含めない判断
- UI / UX / 運用フロー上の意図
- 互換性を壊す変更、データ削除、移行方針
- 複数の妥当な設計案があり、価値判断で選ぶ必要がある場合

質問は不足軸だけに絞る。ローカル調査で分かることや、既に承認された方針を再質問しない。
独立して進められる作業は、回答を待つ間も続ける。

### assume: 仮定して進める

以下をすべて満たす場合は、保守的な仮定で進めてよい。

- 変更が小さく可逆
- 既存パターンに明確に従っている
- テストやレビューで検出できる
- 仮定が外れてもデータ損失、セキュリティ問題、公開 API 破壊につながらない

仮定した場合は、成果報告や PR description に `Assumptions` として残す。

### defer: スコープ外として残す

今回扱わない unknown は、黙って落とさず `Deferred / Not Verified` として残す。
対応が必要なら Issue、TODO、ADR 提案など導入先の記録先へつなぐ。

## 途中: 再計画の停止条件

実装中に以下を見つけたら、手を止めて unknowns を更新し、必要なら計画を組み直す。

- 当初の前提と矛盾するコード、テスト、ログ、ADR を見つけた
- 局所修正のつもりが設計変更・責務変更・データ移行に膨らんだ
- ユーザー意図やプロダクト判断を推測しないと進めない
- 既存パターンに合わない新しい抽象や依存を追加しそうになった
- テストは通るが、要求を満たした根拠が弱い
- 同じ責務境界で修正と指摘が繰り返される

再計画では「続行」「質問」「別案へ切替」「スコープ縮小」「エスカレーション」を明示する。

## 出口: 成果報告に残すもの

完了報告、PR description、調査結果、レビュー返答では、必要に応じて以下を含める。

```markdown
## Verified
- 実行した検証、確認したログ、読んだ記録

## Assumptions
- 未確認のまま置いた仮定

## Not Verified
- 今回確認していないこと

## Follow-up
- 後続 Issue / ADR / 手動確認が必要なこと
```

小さな変更では `Verified` だけで十分な場合もある。複雑な変更や推測を含む変更では、
`Assumptions` と `Not Verified` を省略しない。

## 他ルールとの関係

- `planning-memory.md`: 過去判断・教訓を inspect する入口。
- `testing.md`: test で unknown を解消する検証方針。
- `git-workflow.md`: 実装・PR・エスカレーションの運用境界。
- `documentation-maintenance.md`: unknowns から生じた設計判断や教訓の保存先を層分けする。
- `prompt-optimizer` / `goal-prompt-crafter`: 要件や完了条件が曖昧な場合に unknowns を精緻化する補助。

## 判断フロー

1. その不明点は作業結果に影響するか? → No なら記録不要
2. ローカルのコード・docs・ADR・ログで確定できるか? → Yes なら inspect
3. テストや再現で確定できるか? → Yes なら test
4. ユーザー意図・価値判断・スコープ判断に関わるか? → Yes なら ask
5. 小さく可逆で既存パターンに沿うか? → Yes なら assume として明示
6. 今回扱わないか? → defer として `Not Verified` / `Follow-up` に残す
